1.初次使用者的第一次成功執行GPU運算範例---使用conda
以下提供您 conda + PyTorch 的使用範例：
初始化 conda 然後登出
$ module load anaconda
$ conda init
$ exit
重新登入 (每次登入都要執行module load 不然會沒辦法使用sbatch )
(base)$ module load slurm anaconda
建立 conda 環境並進入該環境
(base)$ conda create --name my-test-env python=3.11
(base)$ conda activate my-test-env
安裝 套件前先修改環境變數，在帳號資料夾下建立tmp資料夾，避免預設tmp塞滿無法安裝程式
echo 'export TMPDIR=$HOME/tmp' >> ~/.bashrc
mkdir -p ~/tmp
source ~/.bashrc
安裝 PyTorch 及所需套件
(my-test-env)$ conda install pytorch torchvision torchaudio pytorch-cuda=11.8 -c pytorch -c nvidia
Job script 範例
#!/bin/bash
#SBATCH -J My-Test-Job # Job Name
#SBATCH -o my-test-job.out # Standard output to file
#SBATCH -e my-test-job.err # Standard error to file
#SBATCH --cpus-per-task=4
#SBATCH --mem=32G
#SBATCH --gres=gpu:1
#SBATCH --time=00:30:00
#SBATCH --gres=gpu:1 # Reserve 1 GPUs for this job
#SBATCH -p trialq # Place job into 'trialq' queue


#==========================
# Load modules
#==========================


module purge
module load anaconda
module list


#==========================
# Anaconda Environment
#==========================


eval "$(conda shell.bash hook)"


conda deactivate
conda activate my-test-env


#==========================
# Execute My Program
#==========================




python /home/user/first.py
送出 job script
$ sbatch first.sh
2.佇列（partition）的選擇
在將工作派送前，可以先下hpcs 確認現在有哪些GPU是空餘的，可以縮短等待時間。
A:
1. **defq (預設佇列)**
   - Job 時間限制：7 天
   - 適合一般計算任務


2. **h200q (高效能佇列)**
   - Job 時間限制：2 天
   - 適合需要較高資源但執行時間較短的任務


3. **trialq (測試佇列)**
   - Job 時間限制：30 分鐘
   - CPU 限制：24 cores
   - 適合測試或除錯使用


4. 申請獨佔式服務的使用者，選擇h200q-rsv 作為 
但JOB時間就沒有限制了

A.
因為這次建置並沒有Infiniband Switch，GPU 計算節點(DGX-CN01~02)單單只裝有Infiniband網路卡，還無法形成Infiniband網路，
如果使用NVIDIA HPC SDK進行編譯程式，那邊HCOLL ...等這些專為Infiniband網路通信優化的函數庫應該就會包含在裡面，
所以在程式執行時HCOLL等可能就會產生這些訊息，如果不會造成程式停止計算的話，其實可以忽略這些信息。 
在你的Email沒有提到是怎麼執行，如果不想要看到這些錯誤的話，可以在執行時試試看下列方式， 
export OMPI_MCA_coll=^hcoll
或
mpirun --mca coll ^hcoll ...

問題二：我們以為用slurm的`--cpus-per-task=10`選項等於指定10個CPU cores，不懂為什麼軟體偵測只有5個CPU core


A:
問題一:
主要是Job Script裡需求ntasks數目大於GPU資源需求引起的，每一個task會執行一個mpi process，並對應跑在一個GPU上，使用者要求ntasks要求5個(--ntasks-per-node=5)，但GPU只要求2顆(--gres=gpu:2)，5個tasks無法分配在2顆GPU上，故無法執行，並產生錯誤訊息「…binding more processes than cpus on a resource…」，所以當時用者要求ntasks要求2個(--ntasks-per-node=5)，對應GPU要求2顆(--gres=gpu:2)，就能正常執行。

因此，問題不在於ntasks-per-node * cpus-per-task = 10 cpus，在於ntasks數目大於需求GPU數目引起的。
另外，也是因為錯誤訊息沒有完整表達問題所在，所以造成誤導與困惑。
問題二：
第二個問題，計算節點在BIOS是有啟用Hyperthread，在OS系統上也就是Thread(s) per core: 2，所以你的疑問主要是因這個BIOS設定的影響而產生的。通常在CPU計算節點會將Hyperthread關閉，但在GPU計算節點則會考慮將這個設定打開，

11.在 HPC 上使用自訂 Docker Image


是否可以使用自訂 Docker image？
可以的，不過我們的系統執行 container 的環境不是 Docker，所以 image 格式需要作轉換處理後才能使用。


具體說明
我們的系統是使用 Slurm 搭配 enroot 來執行 container，而 enroot 只能使用 SquashFS 檔作為 image，因此您需要先將 Docker image 轉換為 SquashFS 檔 (可以參考這裡的指令)，然後上傳至 HPC 後再使用 srun 搭配 --container-image='./my_image.sqsh' 參數執行。


另外，enroot 會需要 container 裡有 shell (e.g. /bin/sh) 才能正常執行，因此若您原本的 container image 中沒有 shell 就會出現錯誤訊息並直接結束，這點與 Docker 不太一樣， Docker 並無強制要求 image 裡要有 shell。
您可以在本地環境先透過以下指令確認 container image 中是不是真的沒有 shell，


docker run --rm my-image-name:my-tag /bin/sh

如果出現類似 /bin/sh: no such file or directory 等訊息則說明沒有 shell。
若確定沒有 shell，則您需要在 build image 時用 docker copy 等方法將 shell 執行檔放到您的 container image 裡再轉換成 SquashFS 檔；或者也可以將轉換好但沒有 shell 的 SquashFS 檔解開、放入 shell 後再重新打包。至於 shell 執行檔可以選用簡單輕量的 busybox 來替代看看。
以下提供您參考步驟，實際使用的指令參數可能仍須根據您的需求調整：
(前置作業) 下載 busybox 並設定可執行權限
wget https://www.busybox.net/downloads/binaries/1.35.0-x86_64-linux-musl/busybox 
chmod +x ./busybox 

(方法 1) 加入 docker copy 重新 build image
在您的 Dockerfile 中加入以下指令，
COPY ./busybox /bin/sh
然後重新執行您的 docker build 指令，其餘步驟(e.g. 轉換成 SquashFS、上傳、執行等)則不變。


(方法 2) 重新打包 SquashFS 檔
解開 SquashFS 檔
unsquashfs ./my_image.sqsh
複製 busybox 並將其作為 shell
mkdir -p ./squashfs-root/bin
cp ./busybox ./squashfs-root/bin/sh
重新打包 SquashFS 檔
fakeroot mksquashfs ./squashfs-root/ ./my_new_image.sqsh -info -processors 1 -noappend -comp xz -Xdict-size 100%
其餘步驟(e.g. 上傳、執行等)則不變。
